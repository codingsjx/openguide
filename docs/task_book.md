## 0. 一句话定位

输入一个开源仓库 URL，OpenGuide 输出一份**带证据、可执行、会陪你走完每一步**的新手贡献路线图：环境怎么搭、测试怎么跑、第一个 issue 怎么选、首个 PR 怎么提。

> 备选 slogan（演示/答辩时二选一）："让第一个 PR 不再是一座山" / "GitHub 上 9000 万新开发者的第一份入门指南，由 AI 现场生成"

| 维度 | 论证 |

## 3. 技术方案：四段管线

### 3.0 核心设计决策

**为什么朴素方案（clone 全文 → LLM 写总结）必败：**

1. 规模失配：数千文件塞不进上下文，噪声淹没信号；
2. 信息类型失配："如何搭环境"分散在 README/CONTRIBUTING/docs/config/workflow 里，全文只有代码拿不到安装步骤；
3. 能力前提失配：新手卡住不会定位问题，指南必须带预期结果与失败分支。

**核心目标**：把非结构化仓库，加工成结构化、可检索、带证据、可分步执行的操作手册。

### 3.1 模块 1：仓库勘探与画像（M0）

- 不 clone 全文，只抓"决策相关"信息：
  - 元数据：语言占比、star/fork、license（GitHub API）
  - 文档面：README、CONTRIBUTING、docs/、LICENSE、SECURITY、.github/ issue 模板与 workflow
  - 构建面：requirements.txt / pyproject.toml / package.json / Cargo.toml / Makefile / Dockerfile / workflows
  - 协作面：近 30 天 commit、good-first-issue / help-wanted 标签 issue
- 输出固定 schema 画像 JSON（前端渲染为"仓库体检卡"，图表化，demo 冲击力强）

```json
{
  "languages": {"python": 0.72, "javascript": 0.28},
  "build": {"tool": "pyproject.toml", "package_manager": "uv", "test_cmd": "pytest"},
  "has_docs": true,
  "has_gfi": {"count": 6, "oldest_days": 3},
  "activity": {"commits_30d": 41, "last_release_days": 12},
  "license": "Apache-2.0",
  "suitability": "promising"
}
```

> 画像先行、全文后置：LLM 不先读任何代码即可决策"适不适合新手、走什么流程"，省 token 且可控。

### 3.2 模块 2：分层视角化索引（M1，技术差异点核心）

朴素仓库 RAG 的缺陷：代码 chunk 对"如何上手"几乎无用；全库检索把"搭环境"和"某行代码逻辑"混为一谈。

对策：按**新手阅读路径**把仓库重组为 4 个视角文档，每视角独立建索引（chromadb）：

| 视角 | 内容来源 | 回答什么 |
|---|---|---|
| V1 入口与约定 | README + CONTRIBUTING + 规范 + license | 贡献流程、协议边界 |
| V2 架构地图 | 目录树 + 顶层 docstring + 主入口 | 代码怎么组织、改哪在哪 |
| V3 可执行路径 | 构建清单 + Makefile/脚本 + workflow + 安装章节 | **怎么跑起来/跑测试/提 PR（新手 90% 卡点）** |
| V4 issue 槽位 | good-first-issue 标题/正文/讨论/涉及文件 | 现在能做什么、第一个任务选哪个 |

关键机制：
- **视角压缩重写**：入库前 LLM 把跨文件的安装/测试步骤聚合成连贯文本，让新手天然跨文件的聚合问题能被单次检索命中；
- **按需激活**：默认只加载 V1+V3；追问功能才检索 V2；挑 issue 才激活 V4。token 与检索相关性受控。

开源组件：
- `chromadb` 向量存储（纯本地、零服务端）
- `sentence-transformers` 本地开源 embedding（默认 `paraphrase-multilingual-MiniLM`）
- （后置可选加分）`tree-sitter` 解析符号表，把 V2 从目录树升级为调用图

### 3.3 模块 3：结构化指南生成（M2，防幻觉核心）

对策一：**画像驱动决策树，不自由发挥**

```
画像 → 适不适合新手？(协议合规 / 文档齐全 / 有 gfi / 活跃)
   ├─ 不适合 → 输出"为什么不适合 + 建议换目标"（帮新手避坑也是价值）
   └─ 适合   → 分 Stage 生成：
        Stage A 环境搭建      （V3，逐条命令 + 期望结果）
        Stage B 测试基线      （V3，"42 passed" 判定标准）
        Stage C 读图选 issue   （V4，2-3 个候选 + 推荐理由）
        Stage D 首次 PR 路径   （V1+V3，fork→clone→branch→commit→push→PR 模板）
```

对策二：**schema 约束输出 + 证据锚点**（Pydantic 模型）

```json
{
  "step_id": 3,
  "title": "安装开发依赖",
  "command": "pip install -e \".[dev]\"",
  "expected": "看到 Successfully installed xxx",
  "fail_hints": ["若提示权限错误→加 --user", "若找不到包→先激活虚拟环境"],
  "evidence": {
    "kind": "file",
    "source": "CONTRIBUTING.md#L22",
    "quote": "Run `pip install -e .[dev]` to install dev deps."
  }
}
```

铁律：**无证据不宣称**。某步找不到来源宁可标"该项目文档缺失，建议去 issue #xx 询问"，不让模型编。

### 3.4 模块 4：分步引导交互（M3，演示形态差异点）

- 前端做**向导卡片流**而非长文：第 n/4 步完成打勾才进下一步；
- 每步卡片三个追问入口：
  - **"这步太粗"** → 重新检索 V3 出细粒度子步骤
  - **"看不懂为什么"** → 检索 V1/V2 解释原理
  - **"报错了"** → 粘贴日志 → 本地规则预判 + LLM 定位到具体文件
- 右侧**证据面板**常驻，当前步骤引用的文件/issue 实时亮起

> 演示卖点："一个会陪你走完第一个 PR 的向导"，而非"一个能回答仓库问题的聊天框"。

## 6. 可验证性设计（国奖命门）

1. **证据锚点**：生成内容全部带 file#line / issue 链接，UI 可点开原始出处；
2. **黄金评估集**：挑 3-5 个特征各异的小仓库（1 Python 库 + 1 前端库 + 1 脚手架项目），人工写好"标准上手指南"；pytest 用规则化指标评测生成质量：
   - 步骤完整率（标准步骤是否全覆盖）
   - 命令可执行性（真实跑一遍验证）
   - 证据命中率（指令能否回溯到真实来源）
   - demo 时直接展示 pytest 通过 = "可验证"的硬证据
3. **真实 PR 彩蛋**：选一个作品之外的小开源仓库，用本产品生成指南并实际走通一个 PR（哪怕是文档补丁），PR 链接进评审材料——完成"作品自己也贡献了开源"的闭环。

### 6.1 评测方法论（对齐上作「安家」的可验证规格）

沿用上作在《风险模型评测脚本》里沉淀的口径，避免"流程烟测冒充模型质量"的失分：

| 分层 | 内容 | 目的 |
|---|---|---|
| L1 烟测 | 假/本地仓库喂固定步骤，只验证"URL→画像→索引→指南→证据锚点"链路通、schema 合法 | 跑 CI/演示，**不代表生成质量** |
| L2 黄金评估集 | 3-5 个人工标准仓库 + 规则化指标（步骤完整率/命令可执行率/证据命中率），记录到 jsonl | 量化生成质量，只报**已人工复核**数字 |
| L3 基准与消融 | 同一批仓库对比"朴素 clone→单 LLM 总结" vs 当前分层管线；对比无证据断言率、命令可执行率、步骤完整率 | 支撑架构叙事 |
| L4 真实贡献 | 真实 PR 走通 + 记录 | 方向三闭环佐证 |

口径红线（与上作一致）：
- 仓库内样例（fixture）只验证流程，**不宣称准确率**；任何质量数字都要能回溯到人工复核过的仓库集。
- 评测运行器 = `scraper/索引/生成/证据校验` 的脚本化后端 + 汇总器；不在页面里"直接展示当前对话"当测试。
- 消融对比必须用同一批仓库、同一基准，避免口径漂移。

### 6.2 提交包清单（评审前逐项核验）

- 可运行源码与依赖锁定（后端 uv/pip lock、前端 pnpm-lock.yaml）
- Docker Compose 部署包 + `.env.example`（**不含真实 Key**）
- 算法说明：仓库画像决策树、四视角索引、schema 约束生成、证据锚点、三步追问
- 测试报告：pytest 输出、黄金评估集结果、消融对比及成本/延迟
- 评测数据与人工标注流程文档（如 `benchmark/README.md`）
- 演示脚本：喂 3 个真实仓库现场出指南
- 3-5 分钟演示视频、作品说明 PDF、隐私与授权说明
- 真实 PR 链接/commit 记录

> 上作提醒的打包硬伤：`.env.example` 与文档里启动路径不一致会导致评审无法复现，提交前做"从干净目录按文档冷启动"演练。

## 7. 开源叙事与克制边界

- **开源叙事**：开源仓库/issue 是燃料，chromadb/sentence-transformers/tree-sitter 是开源管道，产物（结构化指南 + 真实 PR）回馈开源社区。
- **克制边界**：LLM 用商业接口，不硬吹"纯开源模型"。扩展性说明里写"评估集可对比开源模型（如 Qwen）输出质量"点题即可，不过度承诺。这是上作"无证据不宣称"的延续。
- **评测口径边界**：上作红线一并延续——样例/烟测不得宣称模型质量；L2 数字必须能回溯到人工复核过的仓库集；仓库内不做"演示即测试"的混淆。
